## Project

A Stream Deck plugin that controls Logitech Litra lights (Glow, Beam, Beam LX front light) over USB HID, without Logitech's software. It is a fork of a repository its original author abandoned, so some of the code describes decisions nobody here made: `docs/architecture.md` explains the ones that last, and the code's comments the rest. Read them before changing behavior that looks odd.

The plugin is made and checked on macOS, with a Stream Deck + XL running Stream Deck 7.6 and two Litra Beams. The manifest also lists Windows 10, where the plugin isn't checked, so a change shouldn't assume macOS without saying why. The Beam is the plugin's target: defaults use its real values. The Beam LX's front light is supported too, checked on the lamp in #100, and the tests that run on emulated lamps run on both (see [Layout](#layout)). Other models come one at a time, and no work goes into the Glow (see "Supported lamps" in `docs/contributing.md`). The plugin needs neither Logi Options+ nor G HUB, and is checked without them installed.

The plugin isn't on Elgato's Marketplace: `docs/releases.md` describes how a release is made. Releases aren't checked as an installed plugin: their users report what doesn't work ([#21]). Development runs linked from the repo, never installed, so the Deck runs whatever is built from the checked-out branch. That is intended: a change takes effect on the next build and restart.

## Read before changing things

- `docs/user_guide.md`: how the plugin is used, action by action, for its users. A change to what the Deck shows or does, or to a setting, updates it.
- `docs/contributing.md`: how work is done here. Changes go through pull requests, features come with their tests, dependencies are pinned, unused code is removed, a new setting goes in the plugin settings' section of what it reaches, and a text on the lamp screens takes the text style of its role. This file only adds what is specific to Claude.
- `docs/style_guide.md`: the conventions the linters don't enforce (see [Style](#style)).
- `docs/elgato_sdk/`: what the Stream Deck SDK offers and what it doesn't (how actions are registered, the interactions a dial receives, its layouts, how Stream Deck loads the settings pages, its logger, what a key shows), checked against the installed version. Read it before designing how an action behaves on the Deck, and add to it when a change finds out something new about the SDK.
- `docs/logging.md`: what the plugin logs, at which level and with what in each message, where the logs are written and how the files are rotated. A change that logs something new adds it to the contract there.
- `docs/manual_testing/`: the checks that only the Deck can prove, one document per area. Before asking for a test on the Deck, point to the matching document. When a feature needs new manual checks, add them there.
- `docs/releases.md`: how a release is made, from the branch that raises the version to the published release, and where the version is written.
- `docs/architecture.md`: how the plugin's parts fit together, and why they're built that way, such as using `litra` rather than `litra-rs`, finding the lamps afresh on every operation, and what `litra-manager` remembers.

## Layout

- `src/plugin.ts` registers the actions.
- `src/device.ts` is the only module that imports the `litra` library, the third piece of #198. It finds the lamps connected, opens and closes them, gives `litra`'s commands, and makes the reads the plugin does itself: a brightness from two bytes, skipping the reports that aren't its reply (`getBrightnessInLumenSafe`), a Beam LX's serial number over HID++ (`readSerialNumber`, #170), and a write's ACK (`drainAck`). It also names a lamp found, by its model and identity, and gives its path (`plugPath`), and a lamp opened for an operation as the handle a `Lamp` acts on it through (`handleOf`, `LampHandle`). Its tests (`device.test.ts`) run it on emulated lamps.
- `src/litra-manager.ts` is the module the actions ask to change or read the lamps. They import from it, never from `src/device.ts` or `litra` directly. It re-scans the lamps on every call, asks a lamp found without a serial number, such as a Beam LX, for the one it keeps (#170), marks every lamp the plugin knows as connected or not from what it found, and acts only on the ones the plugin knows, which `src/global-settings.ts` hands it as `Lamp`s with `useLamps`: on every one connected, on the lamps it's given by id (a hash of the serial number, `lampId` in `src/lamp-identity.ts`), such as a lamp screen's, or on every one but the lamps it's given, such as a key's that takes in lamps added later. Only `findLamps` sees the lamps it doesn't know. A scene is given one such selection for each of its groups, and each lamp takes the part of the first group that selects it. It always closes the HID handles. It reaches each lamp an operation opens before it changes it (`reach`), lending its `Lamp` a handle, which reads the lamp the first time, and changes the lamps through the `Lamp`s, which make each value's two trips and put back the setting a Beam LX loses when it's turned on (#100). For now, what the keys and dials show, and the toggle's choice, still come from reading the lamps. It asks each lamp's `Lamp` for the cap and the positions it remembers. After every operation that writes to the lamps, it calls the listeners registered with `onLampsChanged`, which is how the Power keys, the step keys' titles, the Brightness and Temperature dials, and the lamp screens follow changes made by any action. It logs what each lamp did, while the actions log what was pressed or turned (see `docs/logging.md`).
- `src/lamp-order.ts` holds the order the plugin goes through the lamps in, by the last 4 characters of their serial numbers, which `litra-manager` sorts them by and the lamp screens step through them in. It imports nothing, so the lamp screens' tests, which replace `litra-manager`, run it as it is.
- `src/lamp-identity.ts` holds who a lamp is, as the plugin names it: `LampIdentity`, what the global settings keep of a lamp, its id (`lampId`, a hash of its serial number) and its labels for the Deck and for the logs. It imports nothing of the plugin's, so `src/lamp.ts` and `src/device.ts` both name lamps from it without importing each other.
- `src/lamp.ts` holds `Lamp`, the first of the objects the refactor in #198 moves the plugin's state into (see `docs/architecture.md`, which describes the plugin as the refactor will leave it). A `Lamp` stands for one lamp. It's built from what the global settings keep of it (`LampIdentity`: its id, model, the end of its serial number and its name), learns its whole serial number when an operation first reaches it (`reachedAs`), and remembers what outlives an operation: its brightness cap, when it may still go back to it, and its positions when it's kept apart. It also holds the lamp's state (`state`: its power, brightness and temperature), its range, and whether the last operation that looked found it, and changes the lamp through the handle `litra-manager` lends it for an operation (`LampHandle`, from `src/device.ts`): `reach` reads the lamp the first time and at a new path, and `setPower`, `sendBrightness` and `readBackBrightness`, `setTemperature` and `blink` make each value's two trips, asking again once, after `READ_AGAIN_MS`, and holding the value asked for when the lamp still doesn't report it. The module also holds the range maths (`percentageInRange`, `percentageToLumen`). It logs what it does to its lamp, and the cap it learns and forgets. The global settings create the `Lamp`s, one for each lamp the plugin knows. Its tests (`lamp.test.ts`) check it on its own, with a fake handle and no lamp.
- `src/global-settings.ts` holds `GlobalSettings`, the plugin's global settings, the second of the objects of #198. It reads them as Stream Deck sends them (`read`), against their schema, holds the lamps the plugin knows as `Lamp`s, by id, which keep what they remember across reads, and is their only writer (`addLamps`, `renameLamp`, `forgetLamp`), saving them through the function it's given. It answers what the keys, dials and lamp screens ask of the settings, such as whether the lamps keep their difference when stepped, the lamps an action key acts on (`actionKeyLamps`), each dial's blink on its lamp screens, and what each cell of the lamp screens shows, and how, and in which text styles, read once each time they change, and tells the listeners registered with `onChanged` each time it reads them, so the keys and the lamp screens follow a page's changes. The module holds the plugin's instance, `globalSettings`, which saves through Stream Deck, and `followGlobalSettings`, which hands `litra-manager` the lamps, reads the settings once the plugin is connected and whenever a page changes them, finds the lamps when the plugin starts knowing none (#194), and then reads every lamp the plugin knows that's connected (`reachEveryLamp`). Its tests (`global-settings.test.ts`) give the class a fake save, and replace the SDK and `litra-manager` to follow it.
- `src/logging.ts` holds the logger every module logs through, instead of `streamDeck.logger`, and the file target that writes it to `logs/litra.log`, rotated by size rather than on every start (see `docs/logging.md`).
- `src/actions/` holds the Power, Brightness, Temperature and Scene actions, the step keys (`step-keys.ts`: Brightness and Temperature Up and Down, one class with a subclass per direction and quantity), the lamp screens (`lamp-screens.ts`) that the Brightness and Temperature dials share, the answers to the plugin settings when they ask for the lamps, blink one, or rename or forget one (`lamp-picker.ts`), which the global settings carry out, and the actions' settings (`settings.ts`): each setting's default and valid values, the global ones included, against which every action reads what Stream Deck sends.
- Unit tests sit next to the file they test (`litra-manager.test.ts`), and run with Vitest. They need no lamps and create no `logs/` folder. `litra-manager.test.ts` runs the real `litra` on the emulated lamps described below, and checks what reaches each lamp and in what order. Its `connect()` reaches the lamps never reached, as the plugin does when it starts, and forgets what that wrote and logged, so each test sees only its own operation. Vitest runs it and `src/integration/actions.test.ts` twice, as the projects `Beam` and `Beam LX` in `vitest.config.mjs`, and every other test file once, as `once`. Their tests plug in lamps of the run's model, which they take with `inject("model")`, unless a test is about one model on its own. The other unit tests replace the modules they build on, such as `litra-manager`, `@elgato/streamdeck` and `src/logging.ts`, with `vi.mock`. The actions' unit tests drive the action they test through `src/test-support/fake-deck.ts`, which places keys and dials, sends each event to the action it belongs to by its `manifestId`, as Stream Deck does, and waits with Vitest's fake timers for everything an interaction sets off. `src/test-support/` holds the shared fakes, and `at`, which the tests use to read an array element, and which fails the test when the element is missing, instead of using `!`.
- `src/integration/` holds the integration tests, which run the real `litra` against emulated lamps, under `npm test` with the unit tests: `litra.test.ts` checks its protocol, and `actions.test.ts` drives the actions through the real `litra-manager`. `src/test-support/emulated-litra.ts` is a lamp that keeps its power, brightness and temperature and answers HID reports as the Beams were measured to (`scripts/probes/README.md`), cap included, and gives the serial number it keeps over HID++, which a Beam LX, emulated or real, leaves out of its USB descriptor, and turns on, as a Beam LX, at the setting it saved 500 ms after it was last switched off, and `fake-node-hid.ts` puts emulated lamps in `node-hid`'s place. The action tests start `plugin.ts` afresh for every test, and drive the actions it registers through the same fake Deck. `vitest.config.mjs` points `litra` at its ESM build, the one the plugin bundles, and has Vitest load it, since otherwise no mock can reach its import of `node-hid`. Every test that runs `litra` loads the code under test through `src/test-support/emulated-lamps.ts`, which loads it afresh, with the fakes mocked by `vi.doMock` after `vi.resetModules()` (a module mocked with `vi.mock` outlives the reset, so the code would keep the first test's fakes), and fails when `litra` didn't get the fake `node-hid`: without it, the tests would write to the lamps plugged in.
- `browser-tests/` holds the browser tests, which load each settings page from the plugin folder in a headless Chrome. They check the controls each page shows, that each control's default and values are the ones `src/actions/settings.ts` takes, the settings it sends, its own and the plugin's global ones, and that its Content-Security-Policy refuses anything remote. `browser-tests/support/` drives Chrome over a pipe rather than a debugging port, and fakes Stream Deck's WebSocket, which keeps the global settings a page reads and saves, and also answers a page that asks for the lamps, and renames and forgets one, as the plugin does, saving the lamps and passing them on to the page, as Stream Deck passes on the plugin's save. It can also send a page an action's settings, as Stream Deck does when they're saved elsewhere. Chrome is found at `CHROME_PATH`, or where macOS or Linux usually install it. The tests run apart from the unit tests, with their own Vitest config, so `npm test` still needs nothing installed.
- `com.daczarne.litra.sdPlugin/` is the plugin folder: `manifest.json`, the settings pages in `ui/` (with the vendored `sdpi-components` in `ui/vendor/`), the icons in `imgs/`, and the custom dial layouts in `layouts/`. `bin/` (the bundle, with its licenses) and `node_modules/` (the native runtime) inside it are build output. Its `.sdignore` lists what `npm run pack` leaves out of the package, besides the CLI's own defaults.
- `scripts/check-ui.mjs` guards the settings pages (see [Supply chain](#supply-chain)). `scripts/check-docs.mjs` checks that every function, class, method and constructor has a doc comment (see the "Doc comments" section of `docs/style_guide.md`). Their tests sit next to them (`check-ui.test.ts`), and run each script with Node, as CI does, in a temporary folder that holds the files it checks (`src/test-support/script-folder.ts`). `scripts/package-files.mjs` decides what the build puts in the plugin folder besides the bundle: the files of `node-hid` that run, and the licenses of everything the plugin ships. Its tests call its functions on a temporary `node_modules`. `scripts/generate-icons.mjs` renders the plugin's icons from the glyphs of `@daczarne/streamdeck-icons` (`daczarne/streamdeck-icons`), which also holds the palette and the Litra icon pack. The lamp screens draw their icons from the same glyphs at runtime, in their cell's text color, so the package is a runtime dependency, bundled into the plugin. A change to a glyph is made there, then taken here by updating the commit the dependency is pinned to and regenerating the icons. `scripts/probes/` holds scripts that ask the lamps directly how they behave, run by hand, with a README on how to run them and read their output.
- `docs/` holds the documents listed in [Read before changing things](#read-before-changing-things).

## Commands

```shell
n auto                    # switch to the Node version in .node-version, and the npm that ships with it
npm ci --ignore-scripts   # install from the lockfile, without install scripts
npm run build             # bundle src/ into the plugin folder and copy node-hid next to it
npm run check:docs        # every function, class, method and constructor has a doc comment
npm run check:ui          # ui/*.html: no remote resources, CSP on every page; vendored file matches its hash
npm run validate          # check:ui, build, streamdeck validate
npm run pack              # check:ui, build, write release/com.daczarne.litra.streamDeckPlugin
npm run icons             # regenerate the icons in imgs/ from scripts/generate-icons.mjs
npm run link              # link the plugin folder into Stream Deck
npm run watch             # rebuild and restart the plugin on change
npm run typecheck         # type-check the sources, the tests, and the build and check scripts
npm run lint              # Biome: lint rules, formatting and import order, without changing anything
npm run format            # Biome: apply the formatting and the import order
npm test                  # run the unit tests and the integration tests
npm run coverage          # the same tests, with a coverage report in the terminal and in coverage/
npm run test:browser      # run the browser tests, which need Chrome
```

When asked for a command, Claude replies with the command and doesn't run it. Steps that change what the Deck runs or shows, like restarting the plugin, are the user's to run, while looking at the hardware.

## Runtime and toolchain

- The plugin runs on Node 24, set by `Nodejs.Version` in `manifest.json`. Stream Deck downloads that runtime into `~/Library/Application Support/com.elgato.StreamDeck/NodeJS/`, whose `manifest.json` lists the exact version (24.22.1 when this was written). A plugin keeps the runtime it started with, so a new one reaches it only on its next restart. `tsconfig.json` extends `@tsconfig/node24`, and `@types/node` is the newest version whose minor doesn't go past that runtime's (24.19 for 24.22), since its minor versions don't follow Node's one for one, and it follows the runtime, not the Node used to build.
- The Node and the npm used to build are pinned in `devEngines` in `package.json` (24.22.1 and 11.19.1, the npm that ships with it), which makes npm refuse any other, to install or to run a script. Node's version is also in `.node-version`, which `n auto` switches to, with its npm, and which CI reads.
- The repo pins TypeScript 6.0, which no longer loads `@types/*` automatically, hence `"types": ["node"]` in `tsconfig.json`. `.vscode/settings.json` points the editor at the repo's TypeScript, so the editor and the build check types with the same version.
- `tsconfig.json` adds stricter checks to `strict`, such as `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and `verbatimModuleSyntax`, for the sources and the tests. `tsconfig.scripts.json` extends it to check, as JavaScript, `rollup.config.mjs`, the Vitest configs and every script, `generate-icons.mjs` included, which takes the glyphs' types from the declarations `@daczarne/streamdeck-icons` ships, and with them the scripts' tests, which import the scripts they test. `tsconfig.json` doesn't allow JavaScript: Rollup's TypeScript plugin reads it, and would start processing JavaScript in the build. `npm run typecheck` runs both configs.
- Biome lints and formats the TypeScript and JavaScript, from `biome.json` (2.5 replaced its `recommended` field with `preset`). Its config has to stay at the repository root: from anywhere else, its type-aware rules report nothing, without a warning. `noFloatingPromises` and `noMisusedPromises` catch unhandled promises, though not an async callback whose promise is ignored, such as one passed to `setTimeout`. The plugin's callback APIs are typed to accept a promise instead (`void | Promise<void>`).
- `node-hid` ships native binaries, so Rollup keeps it external and `copyNativeRuntime` in `rollup.config.mjs` copies the files of it and of `pkg-prebuilds` that run on macOS and Windows into the plugin folder, from the list in `scripts/package-files.mjs`. The build stops when a listed file is missing. A file left off the list breaks a linked plugin too, since Node loads `node-hid` from the plugin folder. A package left off breaks only the installed plugin, because a linked plugin also finds the repo's top-level `node_modules`, and an installed plugin isn't checked ([#21]).

## Supply chain

Supply-chain risk is a hard requirement here:

- No remote code. The settings pages load `sdpi-components` from `ui/vendor/`, pinned by hash in `scripts/check-ui.mjs`. The "Third-party code" section of `README.md` describes how to update it. Never install `sdpi-components` from npm: that package belongs to an unrelated maintainer.
- Each settings page declares a Content-Security-Policy, which `scripts/check-ui.mjs` also holds and checks. It allows scripts only from the plugin folder and connections only to Stream Deck's WebSocket on `localhost`, so inline scripts are blocked: page logic goes in a `.js` file in `ui/`, like `controller-toggle.js`. The "Settings pages" section of `README.md` explains each directive. A change to the policy updates every page, the check and that section.
- Install with `--ignore-scripts`, pin versions, and prefer local copies with recorded hashes. Flag any new dependency, remote resource or broad OS permission, and offer a narrower alternative.
- Node and npm are pinned in `devEngines`, npm at the version that ships with that Node, so neither is installed on its own. npm packages and GitHub Actions are pinned to exact versions, and `@daczarne/streamdeck-icons` to a commit. Each upgrade is its own change: see the "Dependencies" section of `docs/contributing.md`.

## Testing on the hardware

- Build, enable developer mode (`npx streamdeck dev`), `npm run link`, then `npx streamdeck restart com.daczarne.litra`. The actions appear under the Litra category. Developer mode stays on. After that, the `Build and restart` VS Code task (the default build task) runs the build and the restart in one go. A change to `manifest.json` takes effect only once Stream Deck itself is quit and reopened, so mention it whenever a branch changes the manifest.
- Plugin logs are in `com.daczarne.litra.sdPlugin/logs/`, newest in `litra.log`. The SDK's own `com.daczarne.litra.<n>.log` files there hold what the SDK reports itself, such as an uncaught exception. Stream Deck's own log, `~/Library/Logs/ElgatoStreamDeck/StreamDeck.log`, records what it refuses from the plugin, such as a layout it can't load.
- `docs/manual_testing/` holds the checks to run by hand. For example, `settings_pages.md` covers what the browser tests take for granted about Stream Deck, how to open the pages in DevTools to check it, and the debugging port that has to be closed afterwards.
- On a Stream Deck + XL's USB hub (7.5 W), a Beam caps its brightness below 100%, at a level that depends on both the port and the lamp: from 58% to 79% for the Beams it was measured on (see the example in `scripts/probes/README.md`). The cap doesn't change with what the other lamp draws. It does move by a few lumens over time, on the same port ([#164]). Plugged into the computer, a Beam reaches 100%.
- Claude can't see the Deck. The user checks what the keys and the touch strip show, and can share a photo of them, which is enough to judge a layout. Each dial gets 200 × 100 px of the touch strip, and text under about 16 px is hard to read on it ([#8]).
- Opening a Litra over HID needs no macOS permission.

## Workflow

`docs/contributing.md` describes branches, pull requests and tests. On top of it:

- Create branches with `git switch -c`.
- Commit messages explain the why and end with the `Co-Authored-By` trailer for Claude. Commit only when asked.
- `.github/workflows/main.yaml` runs the type check, Biome, the doc comments check, a regeneration of the icons that must change nothing, the unit and integration tests, the browser tests, `npm run validate`, Markdown lint and CSpell on every pull request and on `main`. The browser tests run in a job of their own, beside the others, since they're the slowest and need no build. On `main`, once every check has passed, its last job drafts a release when the version is new (see `docs/releases.md`). Locally, the same checks run in two parts, both as Claude commands and as VS Code tasks: `/lint` and the `Lint` task run the linters (everything but the tests), `/test` and the `Test` task run the unit and integration tests and then the browser tests, and `/ci` and the `CI` task run both. `Test` is VS Code's default test task, so **Tasks: Run Test Task** starts it.
- Write the pull request title and description with the `pr-description` skill.
- Draft issues with the `github-issues` skill, and post them only when asked.
